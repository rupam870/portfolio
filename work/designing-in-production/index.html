workflow

The loop

The slowest part of design here was never Figma. It was the queue between a finished design and a shipped one. So I close it myself.

  1. 01IntentI decide what should change and why, in product terms.
  2. 02Claude CodeWrites the code inside the real repo, following its CLAUDE.md rules.
  3. 03PreviewI check the result live against the design and iterate.
  4. 04ReviewsClaude review, check-quality and ultra-review, every time.
  5. 05CILint and tests run on every push.
  6. 06MergeFrontend and minor backend: I merge. Bigger backend changes: developers review and merge.

# Conventions (excerpt)
- Radix Themes components only
- Design tokens. No hardcoded colours or sizes
- CSS Modules
- One icon set
- Analytics on every click
- Strict lint
- CI on every push
- Never disable a CTA for incomplete input.

stories

Four changes, end to end

story/01 accessibility

Never disable a button. Explain instead.

Problem
A greyed-out submit left people stuck, with no idea why.
Change
The button always works. An empty submit answers inline, even before login.
Why it matters
It became a written rule for the whole repo.
How it was built

The check runs before the login gate, so logged-out visitors see guidance instead of a sign-in wall. The message uses role="alert" for screen readers, and invalid submits are tracked in analytics.

story/02 architecture

AI Edit: from floating window to a real panel.

Problem
AI Edit floated over the scene you were editing and behaved unlike every other tool.
Change
It now opens in the editor's standard side panel.
Why it matters
Consistency came from changing the architecture, not the paint.
How it was built

I removed the drag hook and the portal rendering, and dropped its separate open/closed state from the global store, so it rides on the same panel system as everything else.

story/03 async state

Showing what's generating, everywhere.

Problem
Jobs run in the background across scenes, and people lost track.
Change
Rail tabs get live badges, and the tooltip names what's in flight.
Why it matters
Async state is one of the hardest UX problems in AI products.
How it was built

A new hook watches every scene. Badges have aria-labels, and the animation respects prefers-reduced-motion.

story/04 owning failures

Shipping a regression, and fixing it properly.

Problem
My one-click narrator change dropped the "this affects N scenes" step.
Change
It was reverted, then re-landed with a per-scene regenerate dialog.
Why it matters
Owning the code means owning its failures. The second version is better than the plan.
How it was built

The re-land also needed a small backend change, so regeneration accepts a list of scenes, with a test.

  • v1 dropped the "this affects N scenes" step
  • Rolled back
  • v2: per-scene dialog, backend accepts a list of scenes, plus a test

learning

The vocabulary, one real problem at a time

  • Whenever Claude changes the backend, I ask it to explain exactly what it did, in simple terms, before anything merges.
  • On PRs with migrations, that's how I understood which columns were being added.
  • When a migration conflict came up, I had it explain what that meant. That's how the terms below stuck.
